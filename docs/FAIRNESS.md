# Provably fair draws

The normative algorithm lives in
[`../shared/FAIRNESS_SPEC.md`](../shared/FAIRNESS_SPEC.md). This document
explains *why* it is trustworthy and how to check it.

## The guarantee

For any draw with `n` frozen entries and `w` winners, every entry has an equal
chance of being selected, **provided the seed was fixed before the entries were
known**. The second half is the part most implementations get wrong, and it is
the part this project goes out of its way to enforce.

## The three properties that matter

### 1. The seed is committed before anyone can enter

When a giveaway starts, the bot generates 32 CSPRNG bytes and publishes
`sha256(seed)` in the Discord embed, in the `giveaways.seed_commitment` column,
and on the public page.

The commitment is what makes the seed unfalsifiable. An operator who saw the
participant list and wanted a friendlier seed cannot produce one that hashes to
the already-published commitment — and that commitment was sent to Discord while
the channel was still empty. Anyone reading the message history can check it.

This is why the seed is stored *sealed* at creation time, not chosen at draw time.

### 2. The draw cannot substitute a different seed

The draw runs in three phases:

```
lock   (tx 1)  freeze entries, set locked_at, [reroll: publish new seed]
score          HMAC over the seed READ BACK from the database
reveal (tx 2) write draw + winners + revealed seed
```

Phase 2 calls `read_sealed_seed()`, which `SELECT`s `server_seed` from
`giveaways` and raises `LookupError` if it is absent. It never uses a seed passed
in memory. So even a modified `end()` has no convenient value to substitute —
it would have to update the row, which invalidates the published commitment.

### 3. Scoring has no hidden inputs

```
score = HMAC-SHA256(key=seed, msg="{giveaway_id}:{user_id}:{entry_seq}")  → big-endian integer r
while r >= floor(2^256 / n) * n:        # rejection sampling
    r = HMAC-SHA256(key=seed, msg + ":{attempt}")
score = r // n
```

Ranking is ascending by `(score, user_id, entry_seq)` — a total order, so there is
no ambiguity even if two scores collide (which is cryptographically improbable
but must still be deterministic).

`draw_winners()` accepts exactly: entries, `winner_count`, and optionally a
pre-existing seed. A self-test asserts that signature has not grown a `winner`,
`weight`, `priority` or `rng_seed` parameter.

### Why rejection sampling

`r // n` is only uniform if the range divides evenly. Without the rejection loop,
participants whose entry hash landed in the leftover remainder of `2^256 mod n`
would be slightly more likely to win — a bias of roughly 1 in 2²⁵⁶, negligible in
practice but *not zero*, and not worth defending in an audit.

## What an operator *can* do

Honesty about the limits is part of the guarantee.

| Action | Visible? |
| --- | --- |
| End or cancel a giveaway | Yes — audit log, public history, `ended_reason` |
| Refuse to run a draw | Yes — the giveaway stays un-drawn |
| Disqualify a participant | Yes — recorded with a reason, flagged in the manifest |
| Reroll | Yes — new seed + commitment each time, every round on record |
| Edit rules mid-giveaway | Yes — audit row with before/after |

Grinding rerolls until a favourite wins is possible in principle, but each round
publishes fresh randomness and all rounds stay visible, so it is detectable rather
than hidden.

An operator with direct database write access could forge a draw entirely. The
pre-entry commitment is what makes that detectable — see
[`SECURITY.md`](SECURITY.md) for the full threat model.

## Verify it yourself

### Against a live draw

```bash
curl -s https://<app>/api/giveaways/<id>/verify | jq
```

Returns the seed, commitment, participant digest, the full manifest, and a
recomputed verification block.

### Recompute from scratch

The entire algorithm, ~20 lines:

```python
import hashlib, hmac

def score(giveaway_id, user_id, entry_seq, seed_hex, n):
    key = bytes.fromhex(seed_hex)
    msg = f"{giveaway_id}:{user_id}:{entry_seq}".encode()
    limit = (2**256 // n) * n
    attempt = 0
    r = int.from_bytes(hmac.new(key, msg, hashlib.sha256).digest(), "big")
    while r >= limit:
        attempt += 1
        r = int.from_bytes(hmac.new(key, msg + f":{attempt}".encode(), hashlib.sha256).digest(), "big")
    return r // n

assert hashlib.sha256(bytes.fromhex(seed)).hexdigest() == seed_commitment

lines = sorted(f"{u}:{s}" for u, s in entries)
assert hashlib.sha256("\n".join(lines).encode()).hexdigest() == participant_digest

scored = [(score(giveaway_id, u, s, seed, len(entries)), u, s) for u, s in entries]
scored.sort(key=lambda t: (t[0], t[1], t[2]))
assert [w[1] for w in scored[:winner_count]] == declared_winners
```

Or read it in the browser at `/verify`.

### Prove the two implementations agree

```bash
cd dashboard && npm run fairness:verify
```

This scores `shared/test_vectors.json` — generated by the Python implementation —
with the TypeScript one, and asserts tamper detection:

```
  [ok] algorithm id matches the spec
  [ok] score gw_vector_1:100000000000000001#1
  ...
  [ok] participant digest
  [ok] a correctly derived manifest verifies
  [ok] the derived winner is the lowest score
  [ok] a different seed fails verification
  [ok] an edited score is detected
  [ok] a swapped winner is detected
  [ok] a dropped participant is detected
  [ok] an injected participant is detected
```

If the algorithms ever drift, this fails. Regenerate the vectors after an
intentional change:

```bash
cd bot && python -m giveaway_bot genvectors
```

### Check the draw is not skewed

The bot's self-test runs 120 draws over the same 10 participants and asserts the
winner is spread out (chi-square < 30):

```bash
cd bot && python -m giveaway_bot selftest
# [ok] winner distribution is not skewed
```

## Cryptographic choices

| Choice | Rationale |
| --- | --- |
| 32-byte seed | Full 256-bit space; drawn from `secrets.token_bytes` / WebCrypto |
| HMAC-SHA256, not plain hash | Keyed, so nobody can precompute good scores for a chosen entry set |
| SHA-256 commitment | Standard, cheap, and trivially checkable with `sha256sum` |
| Decimal-string scores | Python `int` and JS `BigInt` agree exactly; `Number` cannot hold 256 bits |
| No PRNG | A seeded PRNG is only as good as its seed; there is no stream to predict |
