# Dashboard (Next.js)

Public giveaway pages, winner proof and the admin panel. Talks to the same
Turso/libSQL database as the Python bot.

## Quick start

```bash
npm install
cp .env.example .env.local        # fill in Turso + Discord values
npm run db:migrate                 # applies shared/migrations
npm run db:seed                    # optional demo data
npm run dev
```

Without Turso credentials the app falls back to a local SQLite file at
`./data/giveaways.db`, so you can click around before provisioning anything.

## Commands

| Command | Purpose |
| --- | --- |
| `npm run dev` | Development server on :3000 |
| `npm run build` / `start` | Production build and server |
| `npm run typecheck` | `tsc --noEmit` |
| `npm run db:migrate` | Apply pending SQL migrations |
| `npm run db:status` | Show applied/pending migrations |
| `npm run db:reset` | **Destructive.** Drop and recreate every table |
| `npm run db:seed` | Insert demo giveaways, participants and a verifiable draw |
| `npm run fairness:verify` | Prove this TypeScript implementation matches the Python one |

`db:migrate` and `fairness:verify` run with Node's native TypeScript stripping, so
they execute the **same** modules the app imports rather than a copy.

## How the dashboard reaches Discord

It doesn't. Admin actions are written to the `command_queue` table and executed
by the Python bot, which re-validates every value against live Discord state
before acting. That means:

* a compromised dashboard session cannot invent new bot capabilities — the bot
  only accepts its whitelisted command kinds
* every action lands in the append-only `audit_log`
* failures are surfaced to the operator instead of being silently swallowed

## Fairness verification

`npm run fairness:verify` checks this app's `src/lib/fairness.ts` against the
vectors generated by the Python implementation:

```
  [ok] score gw_vector_1:100000000000000001#1
  [ok] participant digest
  [ok] a correctly derived manifest verifies
  [ok] a different seed fails verification
  [ok] an edited score is detected
  [ok] a swapped winner is detected
  [ok] a dropped participant is detected
  [ok] an injected participant is detected
```

Regenerate the vectors after any change to the algorithm:

```bash
cd ../bot && python -m giveaway_bot genvectors
```

## Deployment

* **Render** — see [`../render.yaml`](../render.yaml) and `Dockerfile`.
* **Vercel** — import the repo, set the variables below, done. See `vercel.json`.

Required in both:

| Variable | Notes |
| --- | --- |
| `TURSO_DATABASE_URL`, `TURSO_AUTH_TOKEN` | Shared with the bot |
| `DISCORD_CLIENT_ID`, `DISCORD_CLIENT_SECRET` | From the Developer Portal |
| `DISCORD_REDIRECT_URI` | Must match the registered redirect exactly |
| `SESSION_SECRET` | 32+ random chars: `node -e "console.log(require('crypto').randomBytes(32).toString('base64url'))"` |
| `NEXT_PUBLIC_APP_URL` | This deployment's public URL |

### Server Actions and CSRF

Mutations are Next.js Server Actions. They are guarded by an origin allowlist
(`CSRF_TRUSTED_ORIGINS`, auto-populated from `VERCEL_URL` and
`RENDER_EXTERNAL_URL`), a session check, a Manage Server permission check, and a
database-backed rate limit. If the allowlist resolves to empty, origin checks
**fail closed** rather than accepting anything.

## Privacy

Public pages and the public JSON API never expose account timestamps, per-user
message counts, participant identities, or the actual role/channel ID lists —
only counts of them. Participant data is admin-only.
